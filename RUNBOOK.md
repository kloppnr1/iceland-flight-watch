# Iceland Flight Watch

Public page: https://fly.strømsparer.dk (Hetzner server 89.167.101.11, Caddy, `/srv/flight-watch`).

## How data is updated
- **Cloud task (twice a day):** runs `fetch_gf.py cal` (Google Flights calendars via the open-source `fli` tool, `pip install flights click typer rich`), then `UPLOAD_TOKEN=... python3 upload.py cal`, which posts the calendars to `https://fly.xn--strmsparer-2cb.dk/api/cal` (always as a merge, so the server keeps files not sent). `fetch_gf.py` uploads by itself as it goes and stops after 90 minutes (`GF_MINUTES`), so a run fits the 2-hour limit. Calendar pass: new routes first, then the routes whose server calendar is oldest; uploads every 5 routes. Google rate-limits hard (20 calendars took about 30 minutes on 16 Nov), so with 5 destinations (50 routes, 100 calendars) one run refreshes part of the routes and the rest keep their earlier prices until the next run. With time left, the day-by-day pass (flight times, days the calendar missed) covers the next 60 days (`GF_DAY_DAYS`) plus, on routes where Google's calendar is thin further ahead (AAR-PMI showed one day in two months), one 21-day stretch beyond that (`GF_FAR_DAYS`, up to `GF_FAR_MAX` = 240 days ahead, a different stretch each run, so about 4–5 days for a full round), routes with no or the oldest flight times first (`times_at` in the status), uploading each route when done. Days the calendar skipped are filled from the server's last day-by-day prices; a failed calendar search leaves the server's calendar as it was. Google blocks these requests from the Hetzner server (HTTP 429), so this part runs in the cloud.
- **Server (`/opt/flight-watch`):** `api.py` (systemd `flight-watch-api`, 127.0.0.1:8092, Caddy `/api/*`) stores uploads and watches. After each Google upload it queues `run.sh --build-only` (rebuild without Travelpayouts, waits for a running build), so every upload reaches the page. `run.sh` (systemd `flight-watch.service`, timer 4×/day and after each upload) runs `tp.py` (Travelpayouts) and `build.py` (Keflavík board, changes, watches) into `/srv/flight-watch/data`.
- **Destinations:** the page's airport picker ("to …") lists the destinations in `/opt/flight-watch/dests.json` (public copy `data/dests.json`, default Keflavík). "Airports and status…" on the page shows each destination's prices (Google or Travelpayouts, days, flight times, last update; `status` in latest.json) and adds one with the watch PIN (`POST /api/dests`). The API then runs `run.sh <CODE>`, which fetches Travelpayouts prices for that airport only and rebuilds, so first prices show within about a minute (marked as Travelpayouts on the page). `fetch_gf.py` reads the list from the site, does routes without Google prices first and uploads them right away (`{"merge": true}`), then the usual full run. When the Anywhere scan already has the airport (about 140 destinations), `build.py` shows its Google prices (6 months, all and direct-only, no flight times) on the new routes at once, before Travelpayouts (`src` = `anywhere`, "Google (Anywhere scan)" in the airport list). Adding an airport also starts the cloud task "Flight watch – new airport" (`fetch_gf.py --new-only`: 3 routes at a time, all-prices calendars first, each uploaded when done, so a year of Google prices on all 10 routes in about 3–4 minutes after the task starts, direct-only prices a few minutes later; the task runs it in the background, since a foreground command in a cloud session is stopped after 10 minutes) through its API trigger, with `GF_FIRE_URL` (`https://api.anthropic.com/v1/claude_code/routines/<trig_id>/fire`, not the claude.ai page address) and `GF_FIRE_TOKEN` in `.env`. The Delays tab always shows Keflavík flights (it reads Keflavík Airport's board); with another destination selected it says so.
- **Anywhere:** `anywhere.py` (cloud, needs `fli`) checks Google calendars between CPH, BLL, AAR, AAL, HAM, KEF and about 140 destinations worldwide plus every airport added on the page (read from `data/dests.json`, scanned first), both ways, for the next 6 months. Each route's direct-only prices (`fli --stops 0`; skipped when the route has no flights at all) are looked up right after its all-prices calendar, so direct prices reach the page as the scan goes. Followed airports go first, then the routes whose prices on the site are missing or oldest (read from `data/anywhere.json`), so a run stopped before the end (a full run takes about 11–12 hours) still moves the whole list forward day by day. With `UPLOAD_TOKEN` it sends the day-by-day prices to `POST /api/anywhere` every 25 lookups (`cal`, and `dcal` for direct-only; an empty direct calendar means no direct flights), saved in `data/anywhere.json`. Each calendar sent lists the 61-day windows that had prices (`win`); the server replaces only those days and keeps the route's other prices for up to a week (`seg`), so a window Google answers empty does not wipe it. An empty window on a route that has flights is asked again once. Progress is kept in a local `.jsonl` file, so a stopped run continues (within 20 hours); `--upload-only` resends that file. Runs daily as the cloud task "Flight watch – anywhere". On the page there is no separate tab: "Anywhere (every destination)" is the first choice in the top destination menu, and Cheapest flights then shows one card per destination (the cheapest trip there) with the same filters as one airport (round trip or one way, Direct only, bag, airports, stay, dates, max price), plus Sort by (lowest price, best deal, leaving soonest, country A–Z) and an optional "Fly to" list of airports, listed under their country. Each card says how the price compares with the route's usual price (the median of the coming 6 months), how many other days are near it (one way) and how soon it leaves, and has "All prices for <city>" (switches the page to that airport) and "Follow". Watches, Price calendar, Changes and Patterns are per airport and ask for one when Anywhere is picked. Prices come from the twice-daily checks for followed airports and from the Anywhere scan for the rest, direct-only prices included; "Direct only" is remembered in the browser. With Direct only on, a route the scan has not yet checked for direct flights still shows (with all prices), marked "Direct not checked yet" and listed after the confirmed direct results. Every result card (one airport, country, Anywhere, watches) shows per leg a Direct / stops badge (exact stops from flight times; otherwise from the direct-only prices: Direct when the cheapest fare that day is the direct one, else "With stops" plus the direct fare) and, where flight times exist (followed airports, next 60 days), departure–arrival times and flight time.
- **RSA certificates:** some company networks (HTTPS inspection) cannot handle ECDSA certificates and show ERR_SSL_VERSION_OR_CIPHER_MISMATCH. So `/etc/caddy/Caddyfile` starts with the global block `{ key_type rsa2048 }` (set 17 Nov; all certificates on the server were re-issued as RSA then, old ones in `/root/ecdsa-backup`). The same line must be in `deploy/Caddyfile` of the repo that deploys the server's Caddyfile, or its next copy drops it (certificates would then turn ECDSA again at renewal). Caddy's own `caddy validate` fails when run outside the service (basicauth reads secrets from the service's variables); test changes with `systemctl reload caddy`, which keeps the running config if the new one is bad. `health.json` shows each fly name's key type, and the health check reports non-RSA.
- **Health check:** `health.py` runs on the server every 5 minutes (from `autodeploy.sh`, as root) and writes `data/health.json`: HTTPS on both names (certificate valid, days left; a name Caddy has no certificate for gives the browser error ERR_SSL_VERSION_OR_CIPHER_MISMATCH), caddy and flight-watch-api running, free disk. The cloud task "Flight watch – health check" runs `check_health.py` every 3 hours, which also checks that the page data, Google prices, flight times and Anywhere prices are not stale, and sends a push notification only when something is wrong.
- **Admin page (download status):** `https://fly.stromsparer.dk/admin.html` (also linked under "Airports and status…"). Shows each download job (Google prices, Google prices for a new airport, Anywhere scan): running / finished / failed / stopped, progress, current route, errors and the last error, plus the recent runs, the age of every followed route's prices and flight times, Anywhere coverage per home airport, and the server self-check. Problems are listed at the top (same limits as `check_health.py`; a running job with no report for 30 minutes counts as stuck). `fetch_gf.py` and `anywhere.py` report through `jobreport.py` to `POST /api/jobs` (upload token, at most once a minute), saved in `data/jobs.json` (latest report per job + the last 60 finished runs; a run that never reported its end shows as "Ended without report"). The cloud tasks need `jobreport.py` next to the scripts (it is in the repo).
- **Wrong PINs:** after 5 wrong PINs from one address in 15 minutes (or 40 in all in an hour) the API answers 429 until the time has passed; restarting `flight-watch-api` clears it.
- **Archive:** `data/runs/` gets a new file only when the Google prices differ from the last archived check.
- **Tests:** `python3 -m unittest discover tests` (API, watch maths, archive rule; no network needed).
- Secrets live in `/opt/flight-watch/.env` (TP_TOKEN, WATCH_PIN, UPLOAD_TOKEN), not in git.

## Deploy code changes
Push to `main`. The server pulls the repo every 5 minutes (`flight-watch-deploy.timer` → `/opt/flight-watch/autodeploy.sh`, read-only GitHub deploy key `/root/.ssh/flight_watch_deploy`) and installs changed scripts and the page by itself. New systemd units or Caddy changes still need SSH (`flight-watch.caddy` now has `encode zstd gzip`: copy it to the server's Caddy config and `systemctl reload caddy`) (deploy key in `Downloads\sport-tv-deploy` on Martin's PC).

## Open items (16 Nov 2026)
- **Upload token:** replaced 16 Nov. The token is a network secret for `fly.stromsparer.dk` (header `X-Upload-Token`) in the Default cloud environment, and the tasks run with the placeholder `UPLOAD_TOKEN=proxy-injected`. The tasks must run in the Default environment: the secret is not added in the Cowork environment, so uploads from there are refused (403). The scheduled tasks are therefore "Iceland flight watch – Google prices (Default)" and "Flight watch – anywhere (Default)"; the two older tasks without "(Default)" are switched off. To change it: new `UPLOAD_TOKEN` in `/opt/flight-watch/.env` + `systemctl restart flight-watch-api`, and the same value in the network secret.
- **Compression:** copy `flight-watch.caddy` to the server's Caddy config and `systemctl reload caddy`.
- **`flight-watch.service`** is only on the server; copy it into the repo.
- **Old archive files** in `data/runs/` from before the "only new prices" rule were left as they are.
